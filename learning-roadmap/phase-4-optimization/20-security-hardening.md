## 2. 입력 검증

### 2.1 원칙: Trust Nothing

```
규칙: 피어에서 받은 모든 데이터를 검증 없이 사용하지 않는다

이유:
  피어가 보낸 데이터가:
    정상적인 노드에서 온 것일 수도 있고
    공격자가 조작한 것일 수도 있음
  → 구분 불가능
  → 무조건 검증 후 사용
```

### 2.2 메시지 레벨 검증

```
P2P 메시지 수신 시:

Step 1: 크기 검증
  ✅ 메시지 크기 ≤ MAX_MESSAGE_SIZE (4 MB)?
  ❌ 초과 → 즉시 폐기, 피어 점수 차감
  → 메모리 폭탄 방지

Step 2: 매직 넘버 확인
  ✅ 메시지 시작 4바이트 == NETWORK_MAGIC?
  ❌ 불일치 → 다른 네트워크 또는 손상 → 폐기

Step 3: 체크섬 검증
  ✅ payload 해시의 첫 4바이트 == 헤더의 checksum?
  ❌ 불일치 → 전송 중 손상 → 폐기

Step 4: 명령어 확인
  ✅ command가 알려진 명령어인가?
  ❌ 미지의 명령어 → 무시 (에러 아님, 미래 호환)

→ 09번 (네트워크 프로토콜) 참조
```

### 2.3 TX 검증

```
TX 수신 시 검증 순서 (비용 낮은 것부터):

Step 1: 형식 검증 (비용: 매우 낮음)
  ✅ TX 크기 ≤ MAX_TX_SIZE?
  ✅ Input 개수 ≥ 1? (Coinbase 제외)
  ✅ Output 개수 ≥ 1?
  ✅ version이 1~4 중 하나?
  ✅ 직렬화가 올바른가? (파싱 에러 없음?)

Step 2: 중복 검증 (비용: 낮음)
  ✅ 이미 Mempool에 있는 TX 아닌가?
  ✅ 이미 블록에 포함된 TX 아닌가?
  → 중복이면 그냥 무시 (에러 아님)

Step 3: UTXO 검증 (비용: 중간 - 디스크 접근)
  ✅ 모든 Input이 UTXO Set에 존재?
  ✅ 이중 지불 아닌가? (Mempool과도 대조)
  → 07번 §4 참조

Step 4: 에셋 밸런스 검증 (비용: 낮음)
  ✅ 에셋별 Input ≥ Output?
  ✅ 수수료 ≥ 최소 수수료?
  ✅ version별 특수 규칙 충족? (Mint/Burn 등)
  → 13번 §8 참조

Step 5: Script/서명 검증 (비용: 높음 - CPU)
  ✅ 모든 Input의 script_sig가 script_pubkey를 만족?
  ✅ 서명이 유효?
  → 05번 참조

순서가 중요한 이유:
  비용 낮은 검증으로 먼저 걸러내면
  → 비싼 서명 검증을 실행할 TX 수가 줄어듦
  → DDoS 방어 효과
```

### 2.4 블록 검증

```
블록 수신 시:

Step 1: 헤더 검증 (비용: 매우 낮음)
  ✅ 블록 크기 ≤ MAX_BLOCK_SIZE (1 MB)?
  ✅ prev_block_hash가 알려진 블록?
  ✅ timestamp 유효? (미래 2시간 이내, 과거 중앙값 이후)
  ✅ difficulty_target 맞음?
  ✅ PoW 통과? (hash < target)

Step 2: Merkle Root (비용: 낮음)
  ✅ 계산한 merkle_root == 헤더의 merkle_root?

Step 3: TX 전체 검증 (비용: 높음)
  각 TX에 대해 위의 TX 검증 수행
  + Coinbase TX 특수 검증

Step 4: Coinbase 검증 (비용: 낮음)
  ✅ 첫 번째 TX가 Coinbase?
  ✅ Coinbase가 하나만?
  ✅ 보상 ≤ 50 JACK + 수수료?
  ✅ 수수료 분배 50/30/20 맞음?

→ 02번 (데이터 구조) §5, 06번 (PoW) 참조
```

### 2.5 숫자 오버플로우 방지

```
금액 연산 시 오버플로우 주의:

JACK 금액: 8 bytes (int64)
최대값: 9,223,372,036,854,775,807 satoshi
      = 92,233,720,368.54775807 JACK

위험:
  두 금액을 더할 때 오버플로우 가능
  → 음수가 되거나 잘못된 값

방어:
  1. 모든 금액 연산 전에 오버플로우 확인
  2. 뺄셈 전에 underflow 확인 (음수 방지)
  3. 곱셈은 사용 안 함 (정수 나눗셈만)

예시:
  // 안전한 덧셈
  if a > MAX_INT64 - b:
    에러! "금액 오버플로우"
  result = a + b

  // 안전한 뺄셈
  if a < b:
    에러! "잔액 부족"
  result = a - b
```

## 3. 방어적 프로그래밍

### 3.1 Fail-Fast 원칙

```
문제를 발견하면 즉시 중단, 나중에 처리하지 않음

나쁜 예:
  블록 검증 중 이상 발견
  → "일단 넘어가고 나중에 확인하지 뭐"
  → 잘못된 블록이 체인에 적용됨!

좋은 예:
  블록 검증 중 이상 발견
  → 즉시 거부, 피어 점수 차감
  → 절대로 부분 적용하지 않음
```

### 3.2 원자적 상태 변경

```
규칙: 상태 변경은 "전부 성공" 또는 "전부 취소"

블록 적용:
  1. 모든 TX 검증 (아직 상태 안 바꿈)
  2. 전부 유효 확인
  3. Batch Write로 한 번에 상태 변경
  → 중간에 실패하면? → 아무것도 안 바뀜

위험한 패턴:
  TX 하나씩 검증하면서 UTXO Set 업데이트
  → 3번째 TX에서 실패하면?
  → 1, 2번째의 변경을 되돌려야 함 → 복잡

안전한 패턴:
  전체 검증 → Batch → 한 번에 적용
  → 19번 §5.2 참조
```

### 3.3 방어적 역직렬화

```
네트워크에서 받은 바이트를 파싱할 때:

위험: 악의적으로 조작된 데이터
  - 길이 필드가 실제보다 큼 → 버퍼 오버리드
  - 음수 길이 → 메모리 이상
  - VarInt가 비정상적으로 큼 → 메모리 할당 폭탄

방어:
  1. 길이 상한 확인
     VarInt 읽기 → 값 > MAX_ALLOWED? → 거부
  
  2. 남은 바이트 확인
     필드 읽기 전 → remaining_bytes ≥ field_size? → 아니면 거부
  
  3. 총 크기 확인
     파싱 완료 후 → 읽은 바이트 == 메시지 크기? → 아니면 거부

  4. 배열 크기 제한
     Input 개수 > 10000? → 거부
     Output 개수 > 10000? → 거부
     Script 크기 > 10000 bytes? → 거부
```

## 4. Rate Limiting

### 4.1 피어별 제한

```
각 피어의 요청 속도를 제한:

┌──────────────────────┬─────────────────┬──────────────────┐
│ 메시지 종류          │ 제한            │ 초과 시          │
├──────────────────────┼─────────────────┼──────────────────┤
│ TX (tx)              │ 100/분          │ 1분 무시         │
│ 블록 요청 (getdata)  │ 50/분           │ 1분 무시         │
│ inv                  │ 200/분          │ 무시             │
│ ping                 │ 10/분           │ 무시             │
│ addr                 │ 20/분           │ 무시             │
│ 전체 대역폭          │ 10 MB/분        │ 연결 해제        │
└──────────────────────┴─────────────────┴──────────────────┘

구현:
  피어별 카운터 (메시지 타입별)
  1분마다 리셋
  초과 시 해당 메시지 무시 (연결은 유지)
  반복 초과 → 피어 점수 차감 → 결국 연결 해제

→ 12번 §4 (DDoS 방어) 참조
```

### 4.2 Mempool 보호

```
Mempool 리소스 제한:

크기 상한: 300 MB
TX 수 상한: 50,000건
TX당 크기 상한: 100 KB

최소 수수료:
  0.001 JACK/byte
  → 이하 TX는 Mempool에 안 넣음
  → 스팸 TX 방지

수수료 기반 퇴출:
  Mempool 가득 차면 → 수수료 낮은 TX부터 퇴출
  → 중요한 TX가 밀리지 않음

동일 UTXO 사용 TX:
  같은 Input을 쓰는 TX가 이미 있으면?
  → 수수료가 더 높으면 교체 (RBF)
  → 아니면 거부

→ 12번 §4.3 참조
```

### 4.3 CPU 보호

```
서명 검증은 CPU를 많이 씀:

공격: 검증 비용이 높은 TX를 대량 전송
  → 노드 CPU 100%
  → 새 블록 검증 못 함

방어:
  1. 검증 큐 크기 제한
     검증 대기열 > 1000 → 새 TX 일시 거부
  
  2. 검증 타임아웃
     TX 1개 검증 > 5초 → 중단, 거부
  
  3. Script 크기 제한
     script_pubkey > 10,000 bytes → 거부
     script_sig > 10,000 bytes → 거부
  
  4. Script 실행 단계 제한
     OP_CODE 실행 > 10,000단계 → 중단
     → 무한 복잡한 Script 방지
```

## 6. JackpotChain 특수 보안

### 6.1 Exchange TX 보안

```
Exchange TX (version 2) 특수 검증:

  1. 소각 금액 조작 방지
     burn_amount = Input JACK - Output JACK - fee
     → 음수이면 거부
     → 계산과 OP_RETURN 기록 불일치 → 거부

  2. POT 무한 생성 방지
     Mint POT = burn_amount ÷ 100
     → 반드시 정수 (satoshi 단위에서)
     → 100으로 나누어 떨어지지 않으면 거스름돈 처리

  3. version 위장 방지
     version 1 TX에서 POT Mint 시도 → 거부
     → version 별 검증 로직을 명확히 분리

→ 15번 §3 참조
```

### 6.2 가챠 보안

```
가챠 관련 보안 검증:

  Commit TX (version 3):
    ✅ commit_hash 형식 유효? (32 bytes)
    ✅ POT 소각량 정확? (1 POT)
    ✅ 동일 commit_hash 중복 없음?

  Reveal TX (version 4):
    ✅ SHA256(secret) == commit_hash?
    ✅ Commit TX가 실제로 존재?
    ✅ Commit과 Reveal 사이 최소 2블록 간격?
    ✅ Reveal 기한 (50블록) 이내?
    ✅ 당첨금 = Commit 블록 시점 풀 잔액 × 비율?
    ✅ 잭팟 풀 UTXO가 실제로 잭팟 주소의 것?
    ✅ 거스름돈이 잭팟 주소로 돌아가는가?

  채굴자 검열 감지:
    Reveal TX가 Mempool에 오래 체류?
    → 로깅, 경고 (완전 방지는 어려움)

→ 16번 §8, §10 참조
```

### 6.3 잭팟 풀 보호

```
잭팟 풀 UTXO는 특별 보호 대상:

  1. 소비 조건
     version 4 (Reveal) TX에서만 소비 가능
     → 다른 version에서 잭팟 UTXO Input → 거부

  2. 당첨금 상한 (선택적)
     max_payout = min(풀 잔액 × 60%, 상한)
     → 상한 초과 당첨금 → 거부

  3. 풀 잔액 일관성
     잭팟 인덱스 합산 == 잭팟 주소 UTXO 합산?
     → 불일치 감지 시 경고

  4. Coinbase 분배 검증
     매 블록: 수수료 30%가 잭팟 주소로 정확히 들어가는가?
     → 채굴자가 잭팟 몫을 빼돌리는 것 방지
```

## 7. 에러 처리

### 7.1 에러 분류

```
┌──────────────────┬─────────────────────┬──────────────────┐
│ 분류             │ 예시                │ 대응             │
├──────────────────┼─────────────────────┼──────────────────┤
│ 무시 가능        │ 중복 TX 수신        │ 조용히 무시      │
│ (정상 상황)      │ 이미 가진 블록 수신 │                  │
├──────────────────┼─────────────────────┼──────────────────┤
│ 피어 문제        │ 잘못된 TX/블록      │ 거부 + 점수 차감 │
│ (상대방 탓)      │ 타임아웃            │                  │
├──────────────────┼─────────────────────┼──────────────────┤
│ 내부 에러        │ 디스크 쓰기 실패    │ 로깅 + 재시도    │
│ (우리 문제)      │ 메모리 부족         │ 또는 안전 종료   │
├──────────────────┼─────────────────────┼──────────────────┤
│ 치명적 에러      │ DB 손상             │ 로깅 + 즉시 종료 │
│ (복구 불가)      │ Genesis 불일치      │ + 재동기화 필요  │
└──────────────────┴─────────────────────┴──────────────────┘
```

### 7.2 에러 처리 원칙

```
1. 절대 무시하지 않기
   에러를 삼키지 않음 (catch 후 아무것도 안 하기 금지)
   최소한 로깅은 해야 함

2. 피어 에러 ≠ 노드 종료
   피어가 잘못된 데이터 보냄 → 피어 처벌, 노드는 계속
   절대로 피어 입력으로 인해 노드가 크래시하면 안 됨!

3. 내부 에러 → 안전한 상태 유지
   디스크 풀 → 새 블록 적용 중지, 경고
   메모리 부족 → 캐시 줄이기, Mempool 축소

4. 치명적 에러 → 깨끗하게 종료
   DB 손상 → 로그 남기고 종료
   재시작 시 자동 복구 또는 재동기화
```

## 8. 모니터링과 이상 감지

### 8.1 실시간 모니터링 지표

```
=== 네트워크 ===
  연결된 피어 수:          6/6 (목표: 전체)
  피어 평균 점수:          85/100
  수신 메시지/분:          120
  송신 메시지/분:          115
  Ban된 피어:              0

=== 블록체인 ===
  현재 높이:               242,000
  마지막 블록 시간:        3초 전
  평균 블록 타임 (50블록): 15.2초
  포크 감지:               0건
  Orphan 블록:             0개

=== Mempool ===
  대기 TX:                 23건
  크기:                    8 MB / 300 MB
  퇴출된 TX (1시간):       0건

=== 가챠 ===
  활성 Commit (미Reveal):  2건
  최근 당첨:               3시간 전
  잭팟 풀 잔액:            5,432 JACK
  만료된 Commit (1시간):   0건

=== 시스템 ===
  CPU 사용률:              5%
  메모리 사용:             512 MB
  디스크 사용:             5.2 GB / 50 GB
  UTXO 캐시 적중률:        82%
```

### 8.2 이상 감지 경보

```
🟡 주의:
  피어 수 < 4 → 네트워크 분리 위험
  블록 안 옴 > 5분 → 네트워크 문제?
  Mempool 급증 > 100 MB → 스팸 가능성
  캐시 적중률 < 50% → 성능 저하
  단일 피어에서 잘못된 블록 3회 → 악의적 피어?

🔴 경고:
  피어 수 = 0 → 네트워크 단절!
  블록 안 옴 > 30분 → 심각한 문제
  동일 높이에 2개 이상 블록 → 포크!
  잭팟 풀 잔액 급감 → 비정상 당첨?
  디스크 > 90% → 공간 부족 임박
  DB 읽기/쓰기 에러 → 하드웨어 문제?

🚨 긴급:
  UTXO Set 불일치 감지 → 즉시 점검
  Genesis 불일치 → 다른 네트워크에 연결됨!
  잭팟 인덱스 != 잭팟 주소 UTXO 합 → 데이터 손상
```

### 8.3 로깅 전략

```
로그 레벨:

  DEBUG: 모든 메시지 수신/송신, 검증 상세
    → 개발/디버깅 시에만 사용
    → 디스크 빠르게 참

  INFO: 블록 수신, 체인 업데이트, 피어 연결/해제
    → 평시 기본 레벨
    → 1일 ~50 MB

  WARN: 잘못된 TX/블록 수신, 타임아웃, Rate Limit
    → 주의가 필요한 상황
    → 이상 감지의 기초

  ERROR: 디스크 에러, 메모리 부족, DB 에러
    → 즉시 확인 필요

  FATAL: 복구 불가능한 에러
    → 노드 종료 직전 기록

로그 로테이션:
  일일 로테이션, 7일 보관
  또는 파일 크기 100 MB 초과 시 로테이션
```

## 9. MVP 보안 체크리스트

### 9.1 구현 시 필수

```
=== 입력 검증 ===
  □ 메시지 크기 상한 (4 MB)
  □ TX 크기 상한 (100 KB)
  □ 블록 크기 상한 (1 MB)
  □ Input/Output 개수 상한 (10,000)
  □ Script 크기 상한 (10,000 bytes)
  □ 금액 오버플로우 확인
  □ VarInt 상한 확인
  □ 직렬화 남은 바이트 확인

=== TX 검증 ===
  □ UTXO 존재 확인 (이중지불 방지)
  □ 에셋 밸런스 확인
  □ 서명 검증
  □ version별 특수 규칙 (Mint/Burn)
  □ 수수료 ≥ 최소 수수료

=== 블록 검증 ===
  □ PoW 확인
  □ Merkle Root 확인
  □ Coinbase 수수료 분배 (50/30/20)
  □ 블록 내 모든 TX 검증
  □ timestamp 범위 확인

=== 상태 관리 ===
  □ Batch Write (원자적 업데이트)
  □ Undo 데이터 생성
  □ 체인 상태 저장

=== 가챠 ===
  □ Commit-Reveal 간격 검증 (≥ 2블록)
  □ Reveal 기한 검증 (≤ 50블록)
  □ 당첨금 Commit 시점 기준
  □ 잭팟 UTXO 소비 조건
```

### 9.2 운영 시 필수

```
=== 모니터링 ===
  □ 피어 수 모니터링
  □ 블록 수신 간격 모니터링
  □ 잭팟 풀 잔액 추적
  □ 에러 로그 확인 (일 1회)

=== 백업 ===
  □ 체인 데이터 주기적 백업 (주 1회)
  □ 설정 파일 백업
  □ 지갑 키 안전 보관

=== 업데이트 ===
  □ 규칙 변경 시 6노드 동시 업데이트
  □ 활성화 높이 사전 합의
```

## 10. 핵심 요약

### 입력 검증
```
Trust Nothing — 외부 데이터는 모두 악의적이라 가정
크기→형식→중복→UTXO→에셋→서명 순서로 (싼 것부터)
숫자 오버플로우 항상 확인
```

### 방어적 프로그래밍
```
Fail-Fast: 문제 발견 즉시 중단
원자적 상태 변경: Batch Write
방어적 역직렬화: 길이/범위 항상 확인
```

### Rate Limiting
```
피어별 메시지 속도 제한
Mempool 크기/수수료 제한
CPU 보호 (검증 큐, 타임아웃, Script 제한)
```

### 모니터링
```
실시간 지표: 네트워크, 블록체인, Mempool, 가챠, 시스템
3단계 경보: 주의 → 경고 → 긴급
로깅: DEBUG~FATAL, 로테이션 7일
```

### MVP 특수 보안
```
Exchange: 소각 금액 검증, version 위장 방지
가챠: Commit-Reveal 전체 검증 체인
잭팟 풀: 소비 조건, Coinbase 분배 검증
```
