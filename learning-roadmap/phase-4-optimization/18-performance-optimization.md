## 1. TPS 분석

### 1.1 이론적 TPS 계산

```
TPS = Transactions Per Second

기본 파라미터:
  블록 크기: 1 MB (1,048,576 bytes)
  블록 타임: 30초
  평균 TX 크기: ~500 bytes (일반 전송)

계산:
  블록당 TX 수 = 1,048,576 ÷ 500 ≈ 2,097 TX/블록
  TPS = 2,097 ÷ 30 ≈ 70 TPS

TX 타입별 크기 차이:
  일반 전송 (v1):    ~250 bytes (Input 1, Output 2)
  멀티에셋 전송:      ~300 bytes (에셋 데이터 추가)
  Exchange (v2):     ~350 bytes (OP_RETURN 포함)
  Gacha Commit (v3): ~400 bytes (commit_hash 포함)
  Gacha Reveal (v4): ~500 bytes (secret + 잭팟 Input)

가중 평균 (예상 비율):
  v1 70% × 250 = 175
  v2 15% × 350 = 52.5
  v3 10% × 400 = 40
  v4 5%  × 500 = 25
  평균: ~293 bytes

실질 TPS = 1,048,576 ÷ 293 ÷ 30 ≈ 119 TPS
```

### 1.2 비교

```
┌──────────────────┬──────────┬────────────────────┐
│ 체인             │ TPS      │ 블록 타임          │
├──────────────────┼──────────┼────────────────────┤
│ Bitcoin          │ ~7       │ 10분               │
│ Ethereum         │ ~15-30   │ 12초               │
│ JackpotChain     │ ~70-119  │ 30초               │
│ Solana           │ ~65,000  │ 0.4초              │
│ Visa             │ ~1,700   │ (중앙화)           │
└──────────────────┴──────────┴────────────────────┘

JackpotChain이 Bitcoin보다 높은 이유:
  블록 타임이 20배 빠름 (10분 vs 30초)
  블록 크기는 동일 (1 MB)

주의:
  TPS가 높다고 좋은 게 아님
  블록 타임 30초 → 포크율 증가
  → 보안과 성능의 트레이드오프 (06번 참조)
```

### 1.3 MVP에서 실제로 필요한 TPS

```
MVP 환경:
  유저: 6명 (팀원)
  동시 TX: 최대 6건/30초

필요 TPS: 0.4 TPS면 충분

이론 TPS 238 vs 필요 TPS 0.4
→ 600배 여유!
→ MVP에서 TPS는 전혀 병목이 아님
```

## 2. 병목 지점 분석

### 2.1 세 가지 병목

```
┌───────────────────────────────────────────────┐
│                                               │
│   TX 수신 ──→ [네트워크] ──→ 검증 대기열      │
│                                               │
│   검증 대기열 ──→ [CPU] ──→ 검증 완료         │
│                                               │
│   검증 완료 ──→ [디스크] ──→ UTXO Set 업데이트 │
│                                               │
└───────────────────────────────────────────────┘

병목 1: CPU (서명 검증)
병목 2: 디스크 I/O (UTXO 읽기/쓰기)
병목 3: 네트워크 (블록/TX 전파)
```

### 2.2 CPU 병목: 서명 검증

```
ECDSA 서명 검증 = 가장 비싼 연산

비용:
  1회 검증: ~0.1ms (현대 CPU)
  블록당 TX 2000개, TX당 Input 평균 2개:
  → 4000회 검증 × 0.1ms = 400ms

블록 타임 30초 중 400ms:
  → CPU 사용률 1.3% (여유!)

하지만 IBD(초기 동기화)에서는:
  블록을 연속으로 검증 → CPU 100% 사용
  → 병목!

해결:
  → 병렬 서명 검증 (05번 §9.3 참조)
  → 서명 캐싱 (05번 §9.1 참조)
  → 체크포인트 서명 스킵 (11번 §5 참조)
```

### 2.3 디스크 I/O 병목: UTXO 읽기/쓰기

```
TX 검증 시:
  각 Input → UTXO Set에서 조회 (읽기)
  블록 적용 시 → UTXO 추가/삭제 (쓰기)

비용 (SSD 기준):
  랜덤 읽기: ~0.1ms
  랜덤 쓰기: ~0.05ms
  블록당 합계: ~600ms

블록 타임 30초 중 600ms → 2% (여유!)

HDD에서는:
  랜덤 읽기: ~10ms
  블록당: ~40초 > 30초 블록 타임!
  → 심각한 병목! SSD 필수

해결:
  → LRU 캐시 (07번 §7.3 참조)
  → Batch 업데이트 (07번 §8, 11번 §5 참조)
```

### 2.4 네트워크 병목: 블록 전파

```
블록 1 MB를 6개 노드에 전파:

로컬 네트워크 (1 Gbps): 8ms → 무시
인터넷 (100 Mbps): 80ms → 여유
저속 (10 Mbps): 800ms → 블록 타임 대비 5.3%

MVP (로컬 네트워크): 네트워크는 병목 아님!

확장 시:
  → Compact Block (10번 참조)
  → 검증 파이프라이닝 (10번 §5.3 참조)
```

### 2.5 MVP 병목 결론

```
MVP (6노드, 로컬, SSD):
  CPU: 여유 / 디스크: 여유 / 네트워크: 여유
  → 병목 없음! 기능 구현에 집중

IBD (초기 동기화):
  CPU: 병목! / 디스크: 병목!
  → IBD 최적화가 실질적으로 가장 중요
```

## 3. 병렬 처리 전략

### 3.1 뭘 병렬로 할 수 있나?

```
┌─────────────────────────┬───────────┬──────────────────────┐
│ 작업                    │ 병렬 가능 │ 이유                 │
├─────────────────────────┼───────────┼──────────────────────┤
│ 서명 검증 (TX 간)       │ ✅        │ TX끼리 독립적        │
│ 서명 검증 (Input 간)    │ ✅        │ Input끼리 독립적     │
│ Script 실행 (TX 간)     │ ✅        │ Stateless            │
│ UTXO 조회 (TX 간)       │ ✅        │ 읽기는 병렬 가능     │
│ Merkle Root 계산        │ ✅        │ 트리 병합 가능       │
│ 블록 다운로드 (피어 간)  │ ✅        │ 피어별 독립          │
├─────────────────────────┼───────────┼──────────────────────┤
│ UTXO 업데이트           │ ❌        │ 순서 의존 (동일 UTXO)│
│ 블록 간 검증            │ ❌        │ 이전 블록 UTXO 필요  │
└─────────────────────────┴───────────┴──────────────────────┘

핵심: "검증"은 병렬, "상태 업데이트"는 순차
```

### 3.2 병렬 서명 검증

```
블록 내 TX들의 서명을 여러 코어로 동시 검증

효과 (8코어):
  순차: 400ms → 병렬: 50ms (8배!)

적용: 블록 검증, IBD
→ 상세: 05번 §9.3 참조
```

### 3.3 파이프라이닝

```
블록 검증 단계를 겹쳐서 실행:

순차:  Block N [다운→검증→적용]  Block N+1 [다운→검증→적용]
파이프: Block N [다운→검증→적용]
        Block N+1  [다운→검증→적용]

→ IBD에서 전체 시간 단축
→ 상세: 10번 §5.3 참조
```

## 4. 캐싱 전략

### 4.1 캐싱 대상과 효과

```
┌─────────────────────┬──────────┬──────────────┬───────────────┐
│ 캐시 대상           │ 적중률   │ 효과         │ 참조          │
├─────────────────────┼──────────┼──────────────┼───────────────┤
│ UTXO (최근 접근)    │ ~80%     │ I/O 80% 감소 │ 07번 §7.3    │
│ 서명 검증 결과      │ ~30%     │ CPU 30% 절감 │ 05번 §9.1    │
│ Script 패턴 (P2PKH) │ ~95%     │ 파싱 4배↑   │ 05번 §9.2    │
│ 블록 헤더           │ ~99%     │ 즉시 접근    │ 11번 §3      │
│ 피어 주소           │ ~90%     │ 연결 속도↑  │ 08번          │
└─────────────────────┴──────────┴──────────────┴───────────────┘
```

### 4.2 UTXO 캐시 (가장 중요)

```
왜 가장 중요한가?
  TX 검증마다 UTXO 조회 필요 → 디스크 = 느림 → 캐시 = 빠름

관찰:
  최근 생성된 UTXO가 빨리 소비되는 경향
  → "최근 UTXO"를 캐시하면 적중률 80%

LRU 캐시:
  크기: 10,000~100,000 UTXO
  메모리: ~50~500 MB
  적중률: ~80%
  → 디스크 접근 80% 감소!

→ 상세: 07번 §7.3 참조
```

### 4.3 서명 캐시 & Script 패턴

```
서명 캐시:
  Mempool 수신 시 검증 → 블록 포함 시 재검증 스킵
  → 상세: 05번 §9.1 참조

Script 패턴 인식:
  95%+ TX가 P2PKH → 패턴 감지 시 빠른 경로
  P2PKH 빠른 경로: ~0.05ms vs 일반 실행: ~0.2ms (4배)
  → 상세: 05번 §9.2 참조
```

## 6. IBD 최적화 (가장 중요)

### 6.1 왜 IBD가 가장 중요한가?

```
평시 (Normal Operation):
  30초마다 블록 1개 → 여유 충분 → 최적화 불필요

IBD (신규 노드 합류):
  121,000블록 최대한 빨리 → 최적화 안 하면 수시간

→ MVP "성능 최적화"의 핵심 = IBD 최적화
```

### 6.2 IBD 최적화 기법 요약

```
┌──────────────────────────┬───────────┬───────────────┐
│ 기법                     │ 효과      │ 참조          │
├──────────────────────────┼───────────┼───────────────┤
│ 체크포인트 서명 스킵     │ 10배      │ 11번 §5      │
│ UTXO 배치 업데이트       │ I/O 90%↓  │ 11번 §5, 07번│
│ 병렬 서명 검증           │ 8배(8코어)│ 05번 §9.3    │
│ 서명 캐시                │ 30%↓     │ 05번 §9.1    │
│ 병렬 블록 다운로드       │ N배(피어) │ 11번 §4      │
│ Headers-First            │ 가짜 체인 │ 11번 §3      │
│                          │ 조기 거부 │               │
└──────────────────────────┴───────────┴───────────────┘

조합 시: 무최적화 대비 ~50배 빠름

MVP IBD 예상 (11번 §9 참조):
  헤더: ~1초 / 다운로드: ~3분 / 검증: ~5분
  → 총: ~8분
```

## 7. 블록 검증 최적화

### 7.1 검증 단계별 비용

```
블록 1개 (TX 2000개) 검증 비용:

  ┌────────────────────────┬──────────┬──────────┐
  │ 단계                   │ 시간     │ 비율     │
  ├────────────────────────┼──────────┼──────────┤
  │ 헤더 검증 (PoW)        │ 0.01ms   │ 0.001%   │
  │ Merkle Root 계산       │ 2ms      │ 0.3%     │
  │ UTXO 조회 (4000 Input) │ 40ms     │ 6%       │
  │ 서명 검증 (4000개)     │ 400ms    │ 62%      │
  │ Script 실행            │ 100ms    │ 15%      │
  │ 에셋 밸런스 확인       │ 10ms     │ 1.5%     │
  │ UTXO Set 업데이트      │ 100ms    │ 15%      │
  │ 디스크 flush           │ 5ms      │ 0.7%     │
  ├────────────────────────┼──────────┼──────────┤
  │ 합계                   │ ~657ms   │ 100%     │
  └────────────────────────┴──────────┴──────────┘

핵심: 서명 검증 = 62% → 여기 최적화가 가장 효과적
```

### 7.2 최적화 후

```
최적화 적용:
  서명 검증:    400ms → 50ms  (8코어 병렬)
  UTXO 조회:    40ms  → 8ms   (80% 캐시 히트)
  Script 실행:  100ms → 25ms  (P2PKH 빠른 경로)
  UTXO 업데이트: 100ms → 10ms  (배치)

최적화 후: ~100ms/블록
→ 블록 타임 30초 대비 0.3%
→ IBD에서 초당 10블록 검증 가능
```

## 8. 디스크 I/O 최적화

### 8.1 Batch 업데이트

```
문제: UTXO 4000개를 하나씩 → 4000번 디스크 접근
해결: 메모리에 모아서 한 번에 쓰기

  블록 처리 중 → 메모리에 변경사항 축적
  블록 완료 → Batch Write 1회

효과: I/O 4000회 → 1회 (시간: 200ms → 5ms)

IBD에서는 더 공격적:
  100블록마다 flush → I/O 90% 추가 감소

→ 상세: 07번 §8, 11번 §5 참조
```

### 8.2 데이터 압축

```
LevelDB/RocksDB Snappy 압축:
  속도: 250 MB/s (오버헤드 미미)
  비율: ~60% 크기 감소

  UTXO Set: 484 MB → 194 MB
  블록체인: 24 GB → 10 GB

→ 상세: 07번 §8 참조
```

## 9. 최적화 우선순위

### 9.1 MVP 우선순위

```
=== Priority 1~3: 반드시 (쉽고 효과 큼) ===

P1: UTXO 캐시 (LRU)
  효과: 디스크 I/O 80%↓ | 구현: 2시간

P2: Batch UTXO 업데이트
  효과: 디스크 쓰기 40배↓ | 구현: 1시간

P3: P2PKH 빠른 경로
  효과: Script 4배↑ (95% TX) | 구현: 1시간


=== Priority 4~6: 권장 (IBD 성능) ===

P4: 체크포인트 서명 스킵
  효과: IBD 10배↑ | 구현: 1시간

P5: 병렬 서명 검증
  효과: 서명 N배↑ (N=코어) | 구현: 3시간

P6: 서명 캐시
  효과: 중복 검증 30%↓ | 구현: 1시간


=== Priority 7~9: 나중에 (확장 시) ===

P7: Compact Block → 10번 참조
P8: 병렬 블록 다운로드 → 11번 참조
P9: Pruning → 07번 참조
```

### 9.2 효과 vs 구현 비용

```
          구현 쉬움          구현 어려움
효과 큼  │ P1 UTXO 캐시     │ P5 병렬 서명
         │ P2 Batch 쓰기    │ P8 병렬 다운로드
         │ P4 체크포인트     │
─────────┼──────────────────┼──────────────
효과 작음│ P3 P2PKH 경로    │ P7 Compact Block
         │ P6 서명 캐시     │ P9 Pruning

→ 좌상부터 구현 (P1 → P2 → P4 → P3 → P6 → P5)
```

```
  UTXO 적중률:      82% (목표: >70%)

  캐시 메모리:      256 MB

  대기 TX:          45건
  크기:             12 MB / 300 MB
```

### 10.2 병목 감지 & 대응

```
🟡 주의:
  블록 검증 > 3초 → 캐시 크기 확인
  캐시 적중률 < 50% → 캐시 크기 증가
  Mempool > 200 MB → 최소 수수료 확인

🔴 경고:
  블록 검증 > 10초 → 블록 타임 근접! 즉시 조치
  캐시 적중률 < 30% → 메모리 부족 의심
  Mempool 300 MB → 상한 도달, 수수료 낮은 TX 퇴출
  디스크 > 90% → Pruning 고려

대응:
  검증 느림 → 병렬 서명 활성화 / 캐시 증가
  디스크 느림 → Batch 크기 증가 / SSD 확인
  메모리 부족 → 캐시 줄이기 / 프로세스 점검
```

## 12. 핵심 요약

### TPS
```
이론: 140~238 TPS
MVP 필요: 0.4 TPS
→ 600배 여유, TPS는 병목 아님
```

### 병목
```
평시: 병목 없음 (6노드 로컬)
IBD: CPU(서명) + 디스크(UTXO) 병목
→ IBD 최적화가 핵심
```

### 최적화 우선순위
```
먼저: UTXO 캐시, Batch 쓰기, P2PKH 빠른 경로
다음: 체크포인트 스킵, 병렬 서명, 서명 캐시
나중: Compact Block, 병렬 다운로드, Pruning
→ 상세 구현은 각 참조 문서 확인
```

### 메모리
```
합계 ~600 MB / 캐시 최대 ~1.1 GB
일반 노트북으로 충분
```

## 13. 체크리스트

이해했는지 확인:

- [ ] TPS 계산 방법 (블록 크기 ÷ TX 크기 ÷ 블록 타임)
- [ ] 3가지 병목 (CPU, 디스크, 네트워크)
- [ ] 서명 검증이 가장 비싼 이유 (62%)
- [ ] 병렬 가능한 작업 vs 순차 필수 작업
- [ ] UTXO 캐시가 가장 중요한 이유
- [ ] IBD가 평시보다 최적화가 중요한 이유
- [ ] 최적화 우선순위 (효과 vs 구현 비용)
- [ ] MVP 최소 하드웨어 사양
- [ ] 모니터링 경고 기준
