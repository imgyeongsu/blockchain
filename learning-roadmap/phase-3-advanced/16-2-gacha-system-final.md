## 1. 근본 문제: 블록체인 × 랜덤

### 1.1 모순

```
복권에 필요한 것:
  "예측 불가능한 랜덤 값"
  → 아무도 결과를 미리 몰라야 함
  → 조작 불가능해야 함

블록체인의 특성:
  "모든 것이 결정론적이고 투명"
  → 모든 노드가 같은 결과를 계산해야 함
  → 모든 데이터가 공개됨

모순!
  랜덤이 필요한데 모든 게 공개되어 있음
  비밀이 필요한데 비밀을 둘 곳이 없음
  → 이것이 "온체인 랜덤"의 근본적 어려움
```

### 1.2 왜 외부 랜덤을 안 쓰나?

```
방법 1: 서버에서 랜덤 생성
  문제: 서버 운영자가 조작 가능
  → 탈중앙화 아님!

방법 2: 오라클 (Chainlink VRF 등)
  장점: 검증 가능한 랜덤
  문제: 외부 의존성, 구현 복잡, MVP 범위 초과

방법 3: 온체인 데이터로 랜덤 생성
  장점: 외부 의존 없음, 검증 가능
  문제: 조작 가능성 존재
  → 하지만 "충분히 어렵게" 만들 수 있음!
  → JackpotChain의 선택
```

## 2. 시스템 개요

### 2.1 기본 구조

```
JackpotChain 로또:

  참가 방법:
    100 JACK → 1 POT 교환 (멀티에셋 시스템)
    1 POT으로 Commit TX 제출
    6자리 hex 숫자 배열 선택 (각 자리: 0x0 ~ 0xf)

  결과 결정:
    Commit이 포함된 블록 N 기준
    → N+5, N+10, N+15, N+20, N+25, N+30 블록의
      해시 마지막 hex 자리를 순서대로 비교
    
  당첨 기준:
    내가 고른 숫자 vs 각 블록 해시 마지막 자리
    일치 개수에 따라 등수 결정

  잭팟 풀:
    참가비 100 JACK의 80 → 잭팟 풀 적립
    19 → 소각
    1 → 채굴자 보상
```

### 2.2 왜 6개 블록인가?

```
단일 블록 해시 사용 시 문제:
  채굴자가 1개 블록만 조작하면 전체 결과 통제 가능!

6개 블록 분산의 효과:
  → 6개 블록을 모두 조작해야 전체 결과 통제 가능
  → 각 블록이 서로 다른 채굴자에 의해 생성될 가능성 높음
  → 5블록 간격으로 분산 → 약 75분에 걸쳐 결과 확정
  → 단일 블록 조작으로 전체 결과 통제 불가!

블록 간격이 5인 이유:
  너무 짧으면 (간격 1) → 연속 블록을 한 채굴자가 채굴 가능성↑
  너무 길면 (간격 100) → 결과 확인까지 너무 오래 걸림
  간격 5 = 약 25분마다 자리 하나씩 확정 → 균형점
```

## 3. 확률 구조

### 3.1 각 자리 확률

```
각 자리: hex 0x0 ~ 0xf (16가지)
일치 확률: 1/16 = 6.25%

6자리 독립 시행 → 이항분포
```

### 3.2 등수별 확률

```
┌──────┬────────────┬───────────────────┬─────────────────┐
│ 등수 │ 일치 개수  │ 확률 (근사)       │ 보상            │
├──────┼────────────┼───────────────────┼─────────────────┤
│ 1등  │ 6개 전부   │ 1 / 16,777,216    │ 잭팟 풀의 50%   │
│      │            │ ≈ 0.0000000596    │                 │
├──────┼────────────┼───────────────────┼─────────────────┤
│ 2등  │ 5개 일치   │ ≈ 0.0000054       │ 100,000 JACK    │
├──────┼────────────┼───────────────────┼─────────────────┤
│ 3등  │ 4개 일치   │ ≈ 0.000107        │ 20,000 JACK     │
├──────┼────────────┼───────────────────┼─────────────────┤
│ 4등  │ 3개 일치   │ ≈ 0.0045          │ 2,000 JACK      │
├──────┼────────────┼───────────────────┼─────────────────┤
│ 5등  │ 2개 일치   │ ≈ 0.053           │ 300 JACK        │
├──────┼────────────┼───────────────────┼─────────────────┤
│ 6등  │ 1개 일치   │ ≈ 0.304           │ 1 POT 재지급    │
├──────┼────────────┼───────────────────┼─────────────────┤
│ 꽝   │ 0개 일치   │ ≈ 0.68            │ 없음            │
└──────┴────────────┴───────────────────┴─────────────────┘

* 확률 값은 이항분포 기반 근사값. 추후 직접 계산 예정.
```

### 3.3 기대값 (참고용)

```
1등 제외 기대 환급 (1회 참가 기준):
  5등: 0.053  × 300     ≈ 15.9 JACK
  4등: 0.0045 × 2,000   ≈ 9.0  JACK
  3등: 0.000107 × 20,000 ≈ 2.14 JACK
  2등: 0.0000054 × 100,000 ≈ 0.54 JACK

6등 (1 POT 재지급):
  0.304 × (1 POT 기대값) ≈ 별도 계산 필요

  합계 ≈ 27.6 JACK (+ 6등 효과)

참가비 100 JACK 기준:
  → 약 27~33 JACK 수준 환급 (≈ 29%)
  → 약 71%는 풀 누적 + 소각 + 채굴자 보상

⚠️ 기대값은 GPT 추정치. 추후 직접 계산으로 검증 예정.
```

## 4. 랜덤 설계 진화 (V0 → V3)

### 4.1 V0: 순진한 랜덤 (실패 사례)

```
아이디어:
  "Commit 블록 해시를 랜덤 소스로 쓰자"
  결과 = 블록 해시 마지막 자리들

문제: 채굴자 완전 조작
  채굴자가 nonce를 바꿔가며 블록 해시 선택 가능
  → 당첨 나오는 nonce를 골라서 제출
  → 공짜로 100% 당첨 가능!

결론: V0은 완전히 깨진 설계 ❌
```

### 4.2 V1: Commit TX 도입

```
아이디어:
  유저가 숫자를 미래에 결정될 블록 해시와 비교
  → 숫자 선택(Commit) 시점에는 비교 블록들이 아직 존재 안 함!

Commit TX (version 3):
  유저가 6자리 숫자 배열을 제출 (또는 hash(숫자배열))
  → Commit이 Block N에 포함
  → Block N+5, N+10, ..., N+30이 생성되어야 결과 확정

해결된 것: ✅
  유저가 Commit 시점에 미래 블록 해시를 모름
  → 당첨되는 숫자를 미리 고르는 것 불가능!

남은 문제: ⚠️
  채굴자가 자신의 Commit TX를 포함한 블록 N 이후
  N+5, N+10 등을 연속으로 채굴하면 결과 조작 가능
```

### 4.3 V2: 비교 블록 분산

```
아이디어:
  비교 블록을 5 간격으로 분산 (N+5, N+10, ..., N+30)
  → 6개 블록을 한 채굴자가 연속 채굴할 확률 매우 낮음

효과:
  단일 채굴자가 6개 결과 블록을 모두 통제하려면:
  → 네트워크 해시파워의 압도적 다수 필요
  → 현실적으로 불가능 (MVP 6노드 환경에서도)

해결된 것: ✅
  단일 블록 조작으로 전체 결과 통제 불가
  6개 블록 독립 비교 → 조작 범위 제한

남은 문제: ⚠️
  채굴자가 비교 블록 중 하나를 폐기하며 유리한 해시 탐색
  → 1개 자리 조작 가능성 존재 (6자리 중 1자리)
```

### 4.4 V3: 경제적 억제

```
V2의 남은 문제:
  채굴자가 비교 블록을 폐기하며 자리 하나를 유리하게 탐색

V3의 해결:
  블록 폐기 = 블록 보상(50 JACK) 포기!

경제학적 분석:
  1자리 조작으로 6등 → 1등 상승 효과는 제한적
  블록 보상 50 JACK 포기가 훨씬 큰 손실

  1등 직접 노리려면 6개 블록 모두 조작 필요
  → 6 × 50 JACK = 300 JACK 이상 포기
  → 당첨금(잭팟 풀 × 50%)이 수백만 JACK 수준 아니면 비경제적

MVP 현실:
  6노드 = 팀원 → 악의적 조작 동기 낮음
  풀 규모 소형 → 조작 이득 < 블록 보상 포기 비용 (대부분)
  모든 기록 온체인 → 비정상 패턴 즉시 감지
```

## 5. 참가비 흐름 (멀티에셋 시스템)

### 5.1 JACK → POT 교환

```
참가 전 단계:
  100 JACK → Exchange 모듈을 통해 → 1 POT 교환
  (멀티에셋 시스템 참고: 13-multi-asset-system.md)

왜 POT을 별도로 쓰나?
  JACK = 네트워크 경제 전반에 쓰이는 기본 통화
  POT = 로또 참가 전용 토큰
  → 분리하면 로또 경제를 독립적으로 관리 가능
  → POT 소각 시 JACK 공급에 직접 영향 없음
```

### 5.2 참가비 분배

```
참가비 100 JACK 분배:

  80 JACK → 잭팟 풀 적립
  19 JACK → 소각 (디플레이션 효과)
   1 JACK → 채굴자 보상

(비율은 향후 조정 가능)

잭팟 풀의 특성:
  → 대부분 선형 누적 (참가자 수에 비례)
  → 1등 당첨 시 50% 지급 → 큰 변동성 발생
  → 소각 구조로 장기 인플레이션 완화
```

## 6. Commit TX 상세

### 6.1 TX 구조

```
Lotto Commit TX (version 3):

  Input[0]: 유저의 UTXO
    - 1 POT (참가비)
    - JACK (수수료용)

  Output[0]: 유저 거스름돈
    - 남은 JACK

  Output[1]: Commit UTXO
    - jack_value: Min JACK (먼지 방지)
    - 데이터:
        chosen_numbers: [n1, n2, n3, n4, n5, n6]  // 각 0x0 ~ 0xf
        commit_block:   블록에 포함 시 자동 기록
    - script_pubkey: 특수 (Claim 조건)

  수수료: JACK
  POT 소각: 1 POT (Burn)
```

### 6.2 숫자 선택 규칙

```
6자리 hex 배열:
  [0x3, 0xa, 0xf, 0x1, 0x8, 0xc]

각 자리: 0x0 ~ 0xf (16가지 선택지)
순서 중요: 첫 번째 자리 → N+5 블록, 두 번째 → N+10 블록, ...

비교 블록 매핑 (Commit이 Block N에 포함된 경우):
  chosen[0] vs Block N+5  해시 마지막 hex 자리
  chosen[1] vs Block N+10 해시 마지막 hex 자리
  chosen[2] vs Block N+15 해시 마지막 hex 자리
  chosen[3] vs Block N+20 해시 마지막 hex 자리
  chosen[4] vs Block N+25 해시 마지막 hex 자리
  chosen[5] vs Block N+30 해시 마지막 hex 자리
```

### 6.3 예시

```
Alice가 로또 참가:
  chosen = [0x3, 0xa, 0xf, 0x1, 0x8, 0xc]

Commit TX (version 3):
  Input[0]: Alice UTXO (10 JACK + 1 POT)

  Output[0]: 9.9 JACK → Alice (거스름돈)
  Output[1]: 0.01 JACK → Commit UTXO
    데이터: [0x3, 0xa, 0xf, 0x1, 0x8, 0xc]

  수수료: 0.09 JACK
  POT 소각: 1 POT

→ Commit TX가 Block #500에 포함됨
→ Block #505, #510, #515, #520, #525, #530 생성을 기다림
```

### 6.4 Commit UTXO 잠금 조건

```
Commit UTXO는 특수 Script:

  "Commit한 유저의 서명이 있어야 소비 가능"
  + "비교 블록이 모두 확정된 이후에만 소비 가능"
    (Block N+30 이후)

왜 서명이 필요한가?
  타인이 당첨 결과를 보고 당첨된 Commit UTXO를 가로채기 방지
  → 서명이 있으면 유저만 Claim 가능
```

## 7. Claim TX 상세

### 7.1 결과 확정 시점

```
모든 비교 블록이 생성된 후:
  Block N+30 생성 완료
  → 6개 자리 모두 확정
  → 유저가 Claim TX를 제출할 수 있음

결과 계산:
  result_digits = [
    Block(N+5).hash[-1],   // 마지막 hex 자리
    Block(N+10).hash[-1],
    Block(N+15).hash[-1],
    Block(N+20).hash[-1],
    Block(N+25).hash[-1],
    Block(N+30).hash[-1],
  ]

  matches = count(chosen[i] == result_digits[i] for i in 0..5)
  → 일치 개수로 등수 결정
```

### 7.2 Claim TX 구조

```
Lotto Claim TX (version 5):

  Input[0]: Commit UTXO
    - 유저 서명
  Input[1~N]: 잭팟 풀 UTXO (1등 당첨 시에만)

  Output[0]: 보상 → 유저 (당첨 등수에 따라)
  Output[1]: 잭팟 풀 거스름돈 (1등 시)

  수수료: JACK (Commit UTXO의 Min JACK에서)

노드 검증:
  ✅ Commit UTXO가 유효한가?
  ✅ Block N+30 이후인가? (비교 블록 모두 확정)
  ✅ 비교 블록 해시 마지막 자리 계산
  ✅ 일치 개수 → 등수 → 보상 금액
  ✅ 1등이면: Commit 블록 시점 풀 잔액 × 50% 계산
  ✅ 잭팟 풀 UTXO가 실제 잭팟 주소의 것인가?
  ✅ 거스름돈이 잭팟 주소로 돌아가는가?
```

### 7.3 등수별 Claim 처리

```
=== 꽝 (0개 일치) ===
  Claim TX:
    Output[0]: 잔여 Min JACK → 유저 (수수료 제외)
  잭팟 풀: 변화 없음

=== 6등 (1개 일치) ===
  Claim TX:
    Output[0]: 1 POT → 유저 (재지급)
  잭팟 풀: 변화 없음

=== 5등 (2개 일치) ===
  Output[0]: 300 JACK → 유저

=== 4등 (3개 일치) ===
  Output[0]: 2,000 JACK → 유저

=== 3등 (4개 일치) ===
  Output[0]: 20,000 JACK → 유저

=== 2등 (5개 일치) ===
  Output[0]: 100,000 JACK → 유저

=== 1등 (6개 일치) ===
  Commit 블록 시점 잭팟 풀 잔액: P JACK
  당첨금: P × 50%

  Claim TX:
    Input[1~N]: 잭팟 풀 UTXO들 (합산 ≥ P × 50%)
    Output[0]: P × 50% JACK → 당첨자
    Output[1]: 거스름돈 → 잭팟 풀 주소
```

## 8. 치트 방지

### 8.1 지연 치트 방지 (Commit 시점 고정)

```
공격:
  1등 당첨자가 Claim을 늦춰서 풀이 더 쌓인 후 수령

방어:
  당첨금 = Commit 블록 시점의 풀 잔액 기준

  Commit: Block #500 (풀 잔액 100,000 JACK)
  Claim:  Block #1000 (풀 잔액 200,000 JACK)

  당첨금: 100,000 × 50% = 50,000 JACK (Block #500 기준!)
  → 200,000 × 50% = 100,000이 아님!
  → 지연 이득 제로
```

### 8.2 Claim 기한 (Timeout)

```
규칙:
  Block N+30 이후 ~ N+80 이내에 Claim 해야 함
  (50블록 ≈ 25분 여유)

기한 만료 시:
  Commit UTXO → "만료" 상태
  → 아무도 소비 불가
  → POT은 이미 소각됨 (돌려받기 없음)
  → 당첨 권리 소멸

왜 기한이 필요한가?
  1. UTXO Set 비대화 방지
  2. Commit만 하고 Claim 안 하는 스팸 방지
  3. 잭팟 풀 잔액 예측성 확보
```

### 8.3 숫자 공개 타이밍 보안

```
기존 Commit-Reveal과의 차이:
  기존: secret을 hash로 숨김 → Reveal 시 원본 공개
  로또: 숫자 배열을 Commit TX에 그대로 포함

왜 hash가 필요 없나?
  어차피 비교 대상(미래 블록 해시)이 아직 존재하지 않음
  → 숫자를 알아도 결과를 예측 불가능
  → hash로 숨길 필요 없음

그래도 문제 없는가?
  채굴자가 Commit TX를 보고 특정 숫자 배열을 "검열"?
  → 채굴자가 특정 숫자를 가진 TX를 블록에서 빼면?
  → 다른 채굴자가 다음 블록에 포함 가능
  → 검열 지속 시 비용 발생 (기회비용)
  → MVP 환경에서 팀원 채굴 → 검열 동기 없음
```

### 8.4 프론트러닝 방지

```
공격:
  유저의 Commit TX가 Mempool에 보임
  → 공격자가 같은 숫자로 Commit TX를 먼저 제출?

방어:
  Claim UTXO에 유저 서명 필요
  → 숫자가 같아도 유저의 개인키 없이 Claim 불가
  → 프론트러닝해도 Claim 못 함
```

### 9.1 정상 플레이 (꽝)

```
1. Alice: 숫자 선택
   chosen = [0x3, 0xa, 0xf, 0x1, 0x8, 0xc]

2. Alice: 100 JACK → 1 POT 교환

3. Alice: Commit TX 전파
   Input: 1 POT + 10 JACK
   Output: Commit UTXO (chosen 포함) + 거스름돈

4. Block #500에 Commit TX 포함

5. Block #505, #510, #515, #520, #525, #530 순차 생성

6. 결과 확정:
   result = [0x5, 0x2, 0xf, 0x9, 0x1, 0xa]
             ↕     ↕     ↕    ↕    ↕    ↕
   chosen = [0x3, 0xa, 0xf, 0x1, 0x8, 0xc]
   일치:    [✗,   ✗,   ✅,  ✗,   ✗,   ✗]
   
   일치 개수: 1개 → 6등!

7. Alice: Claim TX 제출
   Output: 1 POT → Alice (재지급)
```

### 9.2 정상 플레이 (1등!)

```
1~4. (동일)

5~6. 결과 확정:
   result = [0x3, 0xa, 0xf, 0x1, 0x8, 0xc]
   chosen = [0x3, 0xa, 0xf, 0x1, 0x8, 0xc]
   일치:    [✅,  ✅,  ✅,  ✅,  ✅,  ✅]
   
   6개 전부 일치 → 1등! 🎉🎉🎉

7. 당첨금 계산:
   Commit 블록(#500) 시점 잭팟 풀: 500,000 JACK
   당첨금: 500,000 × 50% = 250,000 JACK

8. Alice: Claim TX 제출
   Input: Commit UTXO + 잭팟 풀 UTXO들
   Output: 250,000 JACK → Alice
           잔여 JACK → 잭팟 풀 주소

9. 잭팟 풀 잔여: 250,000 JACK
```

### 9.3 기한 만료

```
1~6. (동일)

7. Alice가 Claim을 안 함 (잊어버림)

8. Block #580 도달 (N+80, 기한 만료)

9. Commit UTXO: 만료
   → Claim 불가
   → POT 1개: 이미 소각됨
   → 당첨 권리: 소멸
```

## 10. 보안 분석 요약

### 10.1 공격 벡터별 방어 상태

```
┌──────────────────────────┬───────┬────────────────────────────┐
│ 공격                     │ 방어  │ 방어 수단                  │
├──────────────────────────┼───────┼────────────────────────────┤
│ 유저: 당첨 숫자 사전     │ ✅    │ 미래 블록 해시 불가지      │
│ 계산                     │       │ (Commit 시 비교 블록 없음) │
├──────────────────────────┼───────┼────────────────────────────┤
│ 채굴자: 단일 블록 조작   │ ✅    │ 6개 블록 분산              │
│ 으로 전체 결과 통제      │       │ (1개 조작은 1자리만 영향)  │
├──────────────────────────┼───────┼────────────────────────────┤
│ 채굴자: 비교 블록 폐기   │ ⚠️    │ 블록 보상(50 JACK) 포기    │
│ 로 일부 자리 편향        │       │ 비용 발생 (경제적 억제)    │
├──────────────────────────┼───────┼────────────────────────────┤
│ 지연 치트:               │ ✅    │ Commit 블록 시점           │
│ 풀 쌓인 후 Claim         │       │ 잔액 기준 고정             │
├──────────────────────────┼───────┼────────────────────────────┤
│ 비교 블록 검열:          │ ⚠️    │ 다른 채굴자가 다음 블록에  │
│ 채굴자가 해당 블록 폐기  │       │ 포함 / 기회비용 발생       │
├──────────────────────────┼───────┼────────────────────────────┤
│ 프론트러닝:              │ ✅    │ Claim에 서명 필요          │
│ Commit TX 복사 후 Claim  │       │ (개인키 없이 Claim 불가)   │
├──────────────────────────┼───────┼────────────────────────────┤
│ Commit 스팸              │ ✅    │ 100 JACK → 1 POT 비용      │
│                          │       │ + Claim 기한 만료          │
└──────────────────────────┴───────┴────────────────────────────┘

✅ = 구조적으로 방어됨
⚠️ = 경제적으로 억제됨 (완전 방어는 아님)
```

### 10.2 "충분히 공정"의 근거

```
JackpotChain MVP 환경에서:

  1. 채굴자 = 팀원 (6명)
     → 악의적 조작 동기 극히 낮음

  2. 6개 블록 분산
     → 단일 블록 조작으로 전체 결과 통제 불가
     → 1자리 조작해도 5자리는 정상 → 등수 변화 제한적

  3. 블록 보상 포기 비용
     → 합리적 채굴자는 조작 안 함

  4. 모든 기록이 온체인
     → 비정상 패턴 즉시 감지
     → 사후 감사 가능

완전무결은 아니지만:
  → 중앙 서버 복권보다 투명
  → 조작 시도의 비용이 명확
  → "누군가 조작했는지" 사후 검증 가능

이것이 탈중앙화 복권의 가치:
  "조작이 불가능"이 아니라
  "조작했는지 누구나 확인할 수 있다"
```

### 10.3 미래 개선 (MVP 이후)

```
Level 1 (현재): 6개 블록 해시 마지막 자리 비교 + 경제적 억제
  → MVP에 충분

Level 2: 블록 해시 전체 XOR 활용
  result_digit_i = XOR(Block(N+5i).hash의 모든 바이트) & 0xf
  → 마지막 자리만이 아니라 전체 해시 엔트로피 활용

Level 3: VRF (Verifiable Random Function)
  → 채굴자가 검증 가능한 랜덤 생성
  → 조작 불가 + 증명 가능
  → 구현 복잡 (Cardano Ouroboros 참조)

Level 4: 외부 오라클 연동
  → Chainlink VRF 등
  → 완전한 외부 랜덤
  → 외부 의존성 발생
```

## 12. 핵심 요약

### 시스템 구조
```
참가: 100 JACK → 1 POT → Commit TX (6자리 숫자 선택)
결과: 미래 6개 블록 (N+5 간격) 해시 마지막 자리 비교
보상: 일치 개수에 따라 1~6등 / 꽝
```

### 랜덤 설계 진화
```
V0: Commit 블록 해시만 → 채굴자 완전 조작 가능
V1: Commit TX 도입 → 유저 사전 계산 방지
V2: 비교 블록 6개 분산 → 단일 블록 조작으로 전체 통제 불가
V3: + 경제적 억제 → 조작 비경제적으로 만듦
→ 완전무결은 아니지만 "충분히 공정"
```

### 보상 체계
```
1등 (6개): 잭팟 풀 50%
2등 (5개): 100,000 JACK
3등 (4개): 20,000 JACK
4등 (3개): 2,000 JACK
5등 (2개): 300 JACK
6등 (1개): 1 POT 재지급
꽝  (0개): 없음
```

### 탈중앙화 복권의 가치
```
"조작이 불가능"이 아니라
"조작했는지 누구나 확인할 수 있다"
= 투명성 + 검증 가능성
```
