## 1. 공격 벡터 분류

### 1.1 전체 그림

```
블록체인 공격은 크게 4가지 레이어에서 발생:

┌──────────────────────────────────────────┐
│ Layer 4: 응용 (Application)              │
│   - 스마트 컨트랙트 취약점               │
│   - 프론트러닝                           │
│   - 가챠 조작 시도                       │
├──────────────────────────────────────────┤
│ Layer 3: 합의 (Consensus)               │
│   - 51% Attack                          │
│   - Selfish Mining                      │
│   - Block Withholding                   │
├──────────────────────────────────────────┤
│ Layer 2: 네트워크 (Network)             │
│   - Eclipse Attack                      │
│   - Sybil Attack                        │
│   - DDoS                               │
│   - BGP Hijacking                       │
├──────────────────────────────────────────┤
│ Layer 1: 암호학 (Cryptography)          │
│   - 해시 충돌                           │
│   - 개인키 탈취                         │
│   - 양자 컴퓨터 위협                    │
└──────────────────────────────────────────┘

이 문서의 범위:
  Layer 2 (네트워크) + Layer 3 (합의) 중심
  Layer 1은 01-cryptography에서, Layer 4는 Phase 3에서 다룸
```

---

### 1.2 공격자 유형

```
Type A: 외부 공격자
  - 네트워크 참여 없이 공격
  - DDoS, BGP Hijacking
  - 동기: 방해, 경쟁자 견제

Type B: 네트워크 참여자
  - 노드로 참여하면서 공격
  - Eclipse, Sybil
  - 동기: 이중 지불, 정보 수집

Type C: 채굴자
  - 해시파워를 가진 공격자
  - 51%, Selfish Mining
  - 동기: 이중 지불, 추가 수익

Type D: 내부자
  - 개발팀, 운영자
  - 백도어, 규칙 조작
  - 동기: 횡령, 시세 조작

JackpotChain MVP:
  SSAFY 프로젝트 → Type D 위험 낮음
  6개 노드 → Type B 위험 구조적으로 낮음
  주의: Type C (팀원 중 악의적 채굴)
```

## 2. Eclipse Attack

### 2.1 개념

```
Eclipse = "일식" → 태양을 가리듯 노드를 가림

정상 상태:
  피해자 노드가 여러 정직한 노드와 연결
  → 정확한 블록체인 정보 수신

  [정직A] ── [피해자] ── [정직B]
  [정직C] ──     │   ── [정직D]
                 │
             정상적 정보 수신

Eclipse 상태:
  공격자가 피해자의 모든 연결을 장악
  → 피해자가 보는 "세상"을 공격자가 통제

  [공격1] ── [피해자] ── [공격2]
  [공격3] ──     │   ── [공격4]
                 │
             조작된 정보만 수신
             → "일식"된 상태!
```

---

### 2.2 공격 방법

```
=== Step 1: 연결 독점 준비 ===

공격자:
  수백~수천 개의 IP 주소 확보
  (클라우드 VM, 봇넷, VPN 등)
  
  각 IP에서 피해자 노드에 연결 시도
  → Inbound 연결 슬롯을 채움

=== Step 2: Outbound 연결 조작 ===

문제:
  Inbound만 장악해도 Outbound는 피해자가 선택
  → 정직한 노드에 연결될 수 있음

해결 (공격자):
  1. 피해자의 주소 테이블을 공격자 IP로 오염
     → getaddr 응답에 공격자 IP만 포함
  
  2. 피해자 노드를 반복 재시작 유도 (DDoS 후 복구)
     → 재시작 시 Outbound도 공격자에게 연결 확률 증가

  3. DNS Seed 오염 (가능한 경우)
     → 시드 노드가 공격자 IP를 반환하도록

=== Step 3: Eclipse 달성 ===

피해자의 모든 연결 = 공격자
  Inbound 2개: 공격자
  Outbound 6개: 공격자
  
  → 피해자는 공격자가 만든 "가짜 세상"에 갇힘
```

---

### 2.3 Eclipse 이후 가능한 공격

```
공격 1: Double Spending (이중 지불)
  
  상황: 상점 노드가 Eclipse 됨
  
  ① 공격자 → 상점: "100 JACK 보냈어" (TX_A)
     → Eclipse 된 상점: "확인!" (가짜 블록에 포함)
  
  ② 동시에 공격자 → 실제 네트워크: "100 JACK → 내 다른 주소" (TX_B)
     → 실제 블록체인: TX_B 확정
  
  ③ 상점이 물건 배송
  
  ④ Eclipse 해제 후:
     상점: "TX_A가 없어졌다!" → 돈을 못 받음
  

공격 2: 0-Confirmation Attack 강화
  
  Eclipse 없이도 0-conf 공격 가능하지만
  Eclipse이면 100% 성공
  → 상점이 블록 확인을 기다려도 가짜 블록을 보여줄 수 있음


공격 3: 채굴자 분리
  
  채굴자 노드를 Eclipse
  → 채굴자가 낡은 체인 위에서 채굴
  → 해시파워 낭비 → 네트워크 보안 약화
  → 공격자의 상대적 해시파워 증가


공격 4: 정보 차단
  
  특정 TX를 피해자에게 전파하지 않음
  → 선택적 검열
  → 시간에 민감한 TX (TimeLock 등) 방해
```

---

### 2.4 방어

```
방어 1: Outbound 연결 다양성 보장
  
  규칙:
    - 8개 Outbound 중 각각 다른 /16 IP 대역
    - 같은 ASN(자율 시스템)에서 2개 이상 ❌
    - 연결 시간이 오래된 피어 우선 유지
  
  효과:
    공격자가 모든 /16 대역을 확보하기 어려움
    → Eclipse 비용 급증


방어 2: Anchor 연결
  
  개념:
    이전에 성공적으로 통신한 피어를 기억
    재시작 시 이 피어에 먼저 연결
  
  효과:
    재시작을 이용한 공격 방지
    "믿을 수 있는 친구"를 기억


방어 3: 피어 점수 시스템

  각 피어에게 점수 부여:
    + 유효한 블록/TX 전달
    + 빠른 응답
    + 오랜 연결 유지
    - 잘못된 데이터 전달
    - 느린 응답
    - 비정상적 행동
  
  점수 낮은 피어 → 연결 해제 → 새 피어로 교체


방어 4: 여러 소스 교차 검증
  
  블록 높이를 여러 피어에게 확인
  → 대다수가 동의하는 높이 신뢰
  → 1~2개 피어만 다른 정보 → 의심!


방어 5: 하드코딩된 시드 노드
  
  소스코드에 신뢰할 수 있는 노드 IP 내장
  → 최소 1개는 정직한 노드에 연결 보장
  → Eclipse 완전 방지는 아니지만 어렵게 만듦
```

---

### 2.5 JackpotChain에서의 Eclipse

```
MVP 환경 (6개 노드, 로컬):
  Eclipse 위험: 매우 낮음
  
  이유:
    - 노드가 6개뿐 → 전부 팀원
    - IP를 직접 하드코딩 → 가짜 노드 연결 불가
    - 로컬 네트워크 → 외부 접근 차단

확장 환경 (외부 노드 포함):
  Eclipse 위험: 중간
  
  대응:
    - 팀 노드를 Anchor로 설정
    - AWS 브릿지 노드 = 항상 연결
    - 외부 노드의 Outbound 다양성 강제
```

## 3. Sybil Attack

### 3.1 개념

```
Sybil = 다중 인격 → 한 사람이 여러 명인 척

비유:
  온라인 투표에서 한 사람이 계정 1000개 만들어서
  혼자 1000표 행사

블록체인에서:
  공격자가 노드 1000개를 만들어서
  네트워크의 과반수인 것처럼 위장

  실제 노드: 정직 50개 + 공격 10개 = 60개
  Sybil 후: 정직 50개 + 공격 1000개 = 1050개
  
  → 투표하면 공격자가 95% 차지!
```

---

### 3.2 블록체인에서 Sybil이 위험한 이유

```
위험 1: Eclipse 보조
  수천 개 가짜 노드로 피해자 포위
  → Eclipse Attack 성공률 증가

위험 2: 네트워크 분석 (Deanonymization)
  많은 노드를 운영하면 TX의 최초 발신자 추적 가능
  
  정직 노드 A가 TX 생성
  → A의 피어 중 공격자 노드가 가장 먼저 수신
  → "이 TX는 A에서 왔구나!"
  → IP ↔ 주소 연결 → 프라이버시 침해

위험 3: 전파 방해
  가짜 노드가 블록/TX를 느리게 전달
  → 전파 지연 → 포크율 증가
  → 네트워크 불안정

위험 4: 정보 조작
  getaddr 응답에 공격자 IP만 포함
  → 새로 참여하는 노드가 공격자에게만 연결
```

---

### 3.3 왜 완전히 막기 어려운가?

```
P2P 네트워크의 근본 문제:
  "이 노드가 진짜 다른 사람인지 확인할 방법이 없다"

  중앙 서버: 가입 시 신분 확인 가능
  P2P 네트워크: 아무나 노드를 만들 수 있음
  
  → 이것이 탈중앙화의 대가


해결이 어려운 이유:

  방법 1: IP 당 1개 노드 제한
    문제: NAT 뒤에 여러 정직한 노드 가능
    문제: 클라우드로 IP 수천 개 확보 가능 ($)

  방법 2: 신원 확인 (KYC)
    문제: 탈중앙화 위배
    문제: 검열 가능성

  방법 3: PoW로 노드 등록
    문제: 리소스 낭비
    문제: 부유한 공격자에게 유리
```

---

### 3.4 완화 전략 (완전 방지는 불가)

```
전략 1: PoW 기반 보안 (Bitcoin의 해결책)
  
  핵심 통찰:
    Sybil로 노드를 많이 만들어도
    → 해시파워가 증가하지 않음!
    → 합의는 "노드 수"가 아니라 "해시파워"로 결정
  
  결과:
    가짜 노드 1000개 vs 정직한 채굴자 1명
    → 채굴자의 해시파워가 더 크면 채굴자 승리
    → Sybil이 합의에 직접 영향 못 줌


전략 2: 피어 선택 다양성
  
  /16 IP 대역당 연결 수 제한
  → 같은 데이터센터의 노드 다수 연결 방지
  
  ASN (자율 시스템 번호) 다양성
  → 같은 호스팅 업체 노드 제한


전략 3: 행동 기반 평가
  
  노드의 실제 행동으로 판단:
    유효한 블록을 전파하는가?
    올바른 TX를 중계하는가?
    응답 속도가 적절한가?
  
  → 가짜 노드는 대부분 "말만 하고 일은 안 함"
  → 실제 기여도로 판별


전략 4: 연결 수 제한
  
  Inbound 연결 수를 적게 유지
  → Sybil 노드가 들어올 공간 최소화
  → 대신 Outbound는 내가 선택 (다양하게)
```

---

### 3.5 Sybil vs Eclipse 관계

```
Sybil은 Eclipse의 전제 조건:
  
  Eclipse하려면 → 피해자 주변을 포위해야 함
  포위하려면 → 많은 노드가 필요
  많은 노드 → Sybil!
  
  Sybil (수단) → Eclipse (방법) → Double Spend (목적)

따라서:
  Sybil 방어 = Eclipse 방어의 기초
```

## 4. DDoS Attack

### 4.1 개념

```
DDoS = Distributed Denial of Service
  분산 서비스 거부 공격

목적:
  노드를 과부하시켜서 정상 동작 못 하게 만들기

비유:
  식당에 가짜 손님 1000명을 보내서
  진짜 손님이 들어올 수 없게 만들기
```

---

### 4.2 블록체인 대상 DDoS 유형

```
유형 1: 연결 고갈 (Connection Exhaustion)
  
  공격:
    수천 개 TCP 연결 요청 → 연결 슬롯 소진
    정직한 노드가 연결할 수 없음
  
  영향:
    노드 격리 → Eclipse와 유사한 효과
    네트워크 단절


유형 2: 메시지 폭탄 (Message Flooding)
  
  공격:
    유효하지만 쓸모없는 메시지 대량 전송
    예: getdata 요청을 초당 10000번
  
  영향:
    CPU/메모리 과부하
    정상 메시지 처리 지연


유형 3: TX 스팸 (Transaction Spam)
  
  공격:
    최소 수수료의 TX를 대량 생성
    Mempool을 쓸모없는 TX로 가득 채움
  
  영향:
    정상 TX의 확인 지연
    Mempool 메모리 과부하
    수수료 인상 (경쟁)


유형 4: 블록 크기 공격 (Block Size Attack)
  
  공격:
    채굴자가 최대 크기 블록을 계속 생성
    자기 TX로 블록을 채움
  
  영향:
    저장 공간 빠르게 소진
    동기화 시간 증가
    다른 TX 포함 방해


유형 5: 느린 응답 공격 (Slow Loris)
  
  공격:
    연결을 유지하면서 아주 느리게 데이터 전송
    연결 슬롯을 오랫동안 점유
  
  영향:
    새 연결 불가
    리소스 점유
```

---

### 4.3 방어

```
방어 1: Rate Limiting (속도 제한)
  
  피어당 메시지 수 제한:
    inv: 최대 10회/초
    getdata: 최대 10회/초
    ping: 최대 1회/10초
    version: 1회/연결
  
  초과 시 → 경고 → 반복 시 밴


방어 2: 연결 관리
  
  최대 연결 수 제한:
    Inbound: 최대 125개
    Outbound: 8개 (직접 선택)
  
  IP당 연결 수 제한:
    같은 IP에서 최대 1개
    같은 /16 대역에서 최대 2개
  
  핸드셰이크 타임아웃:
    10초 안에 version 교환 안 되면 연결 해제


방어 3: Mempool 관리
  
  Mempool 크기 제한: 300 MB
  최소 수수료율: 0.001 JACK/byte
  TX 만료: 14일 후 자동 제거
  
  꽉 차면:
    수수료 낮은 TX부터 퇴출
    → 스팸 TX가 먼저 제거됨


방어 4: Ban 시스템
  
  Misbehavior 점수:
    잘못된 체크섬: +10
    잘못된 블록: +100  
    핸드셰이크 전 데이터 요청: +50
    Rate Limit 초과: +20
  
  100점 이상: 24시간 밴
  반복 밴: 영구 밴


방어 5: Proof of Work 방어
  
  PoW 자체가 DDoS 방어:
    블록 스팸 → PoW가 필요 → 비용 발생
    TX 스팸 → 수수료 필요 → 비용 발생
  
  → 공격에 실제 비용이 듦
  → 무한 스팸 불가능
```

## 5. 51% Attack

### 5.1 개념

```
51% Attack = 네트워크 해시파워의 과반수 장악

전제:
  Longest Chain Rule
  → 가장 긴 체인 = "진짜"
  → 가장 긴 체인을 만들려면 = 가장 많은 해시파워

따라서:
  51% 해시파워 = 가장 긴 체인을 만들 수 있음
  = 어떤 체인이든 "진짜"로 만들 수 있음
```

---

### 5.2 공격 과정

```
=== Double Spending via 51% ===

시간축 →

공개 체인:
  [...] → [999] → [1000] → [1001] → [1002] → [1003]
                    ↑
                    TX_A: 공격자 → 상점 (100 JACK)
                    상점: "확인! 물건 배송!"

비밀 체인 (공격자만 채굴):
  [...] → [999] → [1000'] → [1001'] → [1002'] → [1003'] → [1004']
                    ↑
                    TX_B: 공격자 → 공격자 (100 JACK, 자기한테)

시점 1: 블록 1000에 TX_A 포함
  → 상점이 확인, 물건 배송

시점 2: 공격자가 비밀 체인을 계속 채굴
  → TX_A 대신 TX_B 포함
  → 51% 해시파워로 공개 체인보다 빠르게 성장

시점 3: 비밀 체인이 더 길어지면 공개!
  → 비밀 체인: 1000' → 1001' → 1002' → 1003' → 1004' (길이 5)
  → 공개 체인: 1000 → 1001 → 1002 → 1003 (길이 4)
  → Longest Chain Rule → 비밀 체인 승리!

결과:
  TX_A (상점에 지불) → 사라짐!
  TX_B (자기에게 지불) → 확정!
  → 물건 + 돈 모두 공격자가 가짐!
```

---

### 5.3 51%로 할 수 있는 것 / 없는 것

```
=== 할 수 있는 것 ===

  ✅ 이중 지불 (Double Spending)
     자신의 TX를 되돌리고 다시 사용

  ✅ TX 검열
     특정 주소의 TX를 블록에 안 넣기
     → 그 주소는 영원히 전송 불가 (51% 유지하는 동안)

  ✅ 빈 블록 채굴
     TX 없는 블록만 만들기
     → 네트워크 마비 (TX 처리 안 됨)

  ✅ 다른 채굴자 보상 탈취
     다른 채굴자의 블록을 무효화
     → 해당 블록 보상 사라짐


=== 할 수 없는 것 ===

  ❌ 남의 코인 훔치기
     개인키 없이 서명 불가능
     → ECDSA는 해시파워와 무관

  ❌ 발행량 변경
     블록 보상은 프로토콜 규칙
     → 50 JACK 이상 받으면 다른 노드가 거부

  ❌ 과거 TX 변경 (깊은 블록)
     이론적으로 가능하지만 비용이 기하급수적
     → 100블록 전 TX → 100블록 분량의 PoW 재계산

  ❌ 네트워크 규칙 변경
     합의 규칙은 모든 노드가 검증
     → 규칙 위반 블록은 다른 노드가 즉시 거부
```

---

### 5.4 경제학적 분석

```
=== 공격 비용 vs 이득 ===

비용:
  1. 해시파워 확보
     - 하드웨어 구매 or 렌탈
     - 전기료
     
  2. 기회비용
     - 정직하게 채굴했으면 받았을 보상
     - 51% 해시파워 = 51%의 정상 수익 포기

  3. 시장 반응
     - 51% 공격 알려지면 코인 가격 폭락
     - 공격자의 보유 코인 가치도 하락

이득:
  1. 이중 지불 금액
  2. 검열 수수료 (이론적)

일반적 결론:
  보유 코인 가치 하락 > 이중 지불 이득
  → 대규모 PoW 네트워크에서는 비경제적

BUT:
  JackpotChain (소규모):
    해시파워 적음 → 공격 비용 낮음
    코인 가치 낮음 → 가격 하락 손실도 작음
    → 51% 공격 상대적으로 쉬움 ⚠️


=== JackpotChain 51% 시나리오 ===

MVP (6개 노드):
  팀원 6명 × 1대 = 총 6대 PC
  3대만 확보하면 50%+
  
  하지만:
    - 팀 내부 → 신뢰 기반
    - 실습 환경 → 실제 가치 없음
    → 위험 극히 낮음

실운영 시:
  외부 채굴자 참여 → 해시파워 분산
  → 51% 확보 비용 증가
  → 코인 가치 상승하면 공격 비경제적
```

---

### 5.5 방어

```
방어 1: 충분한 확인 수 대기
  
  확인 수가 많을수록 51% 공격 비용 증가
  
  JackpotChain 권장:
    소액: 6 확인 (1.5분)
    고액: 12 확인 (3분)
    거래소: 30+ 확인 (7.5분+)


방어 2: 체크포인트
  
  개발팀이 확정된 블록 해시를 하드코딩
  → 체크포인트 이전으로 되돌릴 수 없음
  → 긴 Reorg 공격 방지


방어 3: 해시파워 분산 장려
  
  - 채굴 풀 독점 방지
  - 개인 채굴 장려
  - 해시파워 집중 모니터링


방어 4: 이상 감지
  
  모니터링:
    - 갑작스러운 해시파워 변동
    - 비정상적으로 긴 Reorg
    - 이전에 확인된 TX의 소멸
  
  감지 시:
    - 경고 발생
    - 확인 수 요구 증가
    - 입출금 일시 중단 (거래소)
```

## 6. Selfish Mining

### 6.1 개념

```
Selfish Mining = 이기적 채굴
  발견한 블록을 바로 공개하지 않고 숨기는 전략

정직한 채굴:
  블록 발견 → 즉시 전파 → 보상 수령

이기적 채굴:
  블록 발견 → 숨김 → 전략적 시점에 공개
  → 정직한 채굴자의 블록을 무효화
  → 자기 블록만 살리기
```

---

### 6.2 공격 과정

```
=== Selfish Mining 시나리오 ===

상황: 공격자 해시파워 30%, 정직 70%

Round 1:
  공개 체인: [...] → [999]
  비밀 체인: [...] → [999]
  
  공격자가 [1000S] 발견! → 숨김 (비밀 체인에만)
  공개 체인: [...] → [999]
  비밀 체인: [...] → [999] → [1000S]

Round 2 (Case A): 정직이 [1000H] 먼저 발견
  공개 체인: [...] → [999] → [1000H]
  비밀 체인: [...] → [999] → [1000S]
  
  → 공격자: [1000S]를 즉시 공개!
  → 네트워크: [1000H] vs [1000S] 경쟁
  → 공격자의 피어 중 일부가 [1000S]를 먼저 봄
  → 네트워크 분열 → 다음 블록이 결정

Round 2 (Case B): 공격자가 [1001S]도 발견
  공개 체인: [...] → [999]
  비밀 체인: [...] → [999] → [1000S] → [1001S]
  
  → 공격자: 2블록 리드!
  → 정직이 [1000H] 발견해도:
    공격자 [1000S] → [1001S] 공개
    → Longest Chain Rule → 공격자 승리!
    → [1000H] 무효화됨
    → 정직 채굴자의 전기료 = 낭비!
```

---

### 6.3 왜 유리한가?

```
핵심:
  Selfish Mining은 자기 블록의 비율을 해시파워 비율보다 높게 만듦

예시:
  공격자 해시파워: 30%
  정직한 채굴: 블록의 30%가 공격자 것
  이기적 채굴: 블록의 33~40%가 공격자 것!

이유:
  정직한 채굴자가 발견한 블록을 무효화시킴
  → 그 블록에 들인 에너지 = 낭비
  → 상대적으로 공격자 비율 증가

수학적으로:
  α = 공격자 해시파워 비율
  γ = 포크 시 공격자 블록을 선택하는 네트워크 비율
  
  Selfish Mining이 유리한 조건:
    α > (1 - γ) / (3 - 2γ)
  
  γ = 0일 때: α > 1/3 (33%)
  γ = 0.5일 때: α > 1/4 (25%)
  γ = 1일 때: α > 0 (이론적으로 항상 유리)

  Bitcoin의 경우:
    γ ≈ 0이면 33% 이상부터 유리
    즉 51%까지 안 가도 이득!
```

---

### 6.4 방어

```
방어 1: Uniform Tie-Breaking
  
  같은 높이의 두 블록이 경쟁하면:
    정책: "먼저 본 블록" 대신 "랜덤 선택"
    → γ를 0.5로 만듦
    → Selfish Mining 임계값을 25%로 올림

방어 2: Timestamp 분석
  
  블록 타임스탬프가 비정상적이면 의심:
    "2초 전에 채굴했는데 왜 이제야 공개?"
    → Selfish Mining 징후

방어 3: 네트워크 전파 속도 향상
  
  전파가 빠를수록:
    정직한 블록이 더 빨리 퍼짐
    → 공격자가 숨긴 블록을 늦게 공개할수록 불리
    → γ 감소 → 공격 어려워짐

방어 4: 해시파워 분산
  
  단일 채굴자/풀이 33% 이상 차지 방지
  → 모니터링 + 사회적 합의
```

## 7. Block Withholding Attack

### 7.1 개념

```
Block Withholding = 블록 보류 공격
  채굴 풀 내에서의 배신 행위

채굴 풀 구조:
  풀 매니저: 작업 배분 + 보상 분배
  풀 멤버: PoW 작업 수행 + 부분해 제출
  
  부분해 (Share): 쉬운 난이도를 만족하는 해시
    → "나 열심히 일하고 있어요" 증명
    
  전체해 (Solution): 실제 블록 난이도를 만족하는 해시
    → 블록 발견!

공격:
  악의적 멤버가 풀에 참여
  → Share는 정상 제출 (보상 받기)
  → Solution 발견해도 제출 안 함! (블록 보류)
  → 풀의 블록 발견율 하락
  → 다른 멤버들의 수입 감소
```

---

### 7.2 영향

```
피해:
  풀의 실제 해시파워: 100 TH/s
  공격자 해시파워: 10 TH/s (10%)
  
  정상 시:
    풀 블록 발견: 100% 효율
    
  공격 시:
    풀 해시파워 기여: 100 TH/s (공격자 포함)
    풀 블록 발견: 90 TH/s 효율 (공격자 Solution 미제출)
    
    결과:
      풀 수입 10% 감소
      공격자: Share 기반 보상은 정상 수령
      다른 멤버: 수입 감소 (공격자 때문)

동기:
  1. 경쟁 풀 방해 (풀 A가 풀 B에 스파이 파견)
  2. 풀 수수료 없이 채굴 (보상만 받고 기여 안 함)
```

---

### 7.3 JackpotChain 관련성

```
MVP:
  채굴 풀 없음 (각자 개인 채굴)
  → Block Withholding 해당 없음

확장 시:
  풀이 생긴다면:
    Share 검증 강화
    풀 멤버 평가 시스템
    비정상적 Share/Solution 비율 감지
```

## 8. BGP Hijacking

### 8.1 개념

```
BGP = Border Gateway Protocol
  인터넷 라우팅의 핵심 프로토콜
  "이 IP 대역은 내 네트워크를 통해 접근해" 라고 광고

BGP Hijacking:
  공격자가 거짓 BGP 광고를 전파
  → 특정 IP 대역의 트래픽을 가로채기
  → 블록체인 노드 간 통신을 중간에서 조작

비유:
  도로 표지판을 조작해서
  모든 차가 공격자의 검문소를 지나가게 만드는 것
```

---

### 8.2 블록체인에 대한 영향

```
영향 1: 네트워크 분할 (Partition)
  
  국가 A의 노드 ←× 차단 ×→ 국가 B의 노드
  
  결과:
    두 그룹이 독립적으로 체인 성장
    → 차단 해제 시 긴 Reorg 발생
    → 이중 지불 가능

영향 2: 선택적 메시지 지연
  
  블록 전파를 10초 지연
  → JackpotChain (15초 블록타임)에서는 심각
  → 포크율 급증
  → 채굴자 수익 불안정

영향 3: Eclipse 보조
  
  BGP Hijacking + Sybil = 강력한 Eclipse
  → 피해자의 모든 트래픽을 공격자가 중계
```

---

### 8.3 방어

```
방어 1: 암호화된 통신
  
  TLS/SSL로 노드 간 통신 암호화
  → 중간자가 내용을 읽거나 수정 못 함
  → 그러나 차단은 여전히 가능

방어 2: 다중 경로 (Multi-path)
  
  여러 네트워크 경로로 동시 연결
  → 하나가 Hijack 되어도 다른 경로로 정보 수신
  → Tor, VPN 병행

방어 3: 이상 감지
  
  레이턴시 갑자기 증가 → BGP 변경 의심
  특정 피어만 다른 체인 → 분할 의심
  → 경고 & 추가 피어 연결

방어 4: RPKI (Resource Public Key Infrastructure)
  
  BGP 광고에 암호학적 서명
  → 거짓 광고 검증 가능
  → 아직 전체 도입되지 않음 (인터넷 인프라 문제)
```

## 9. Transaction-Level 공격

### 9.1 Double Spending 변형

```
Type 1: Race Attack (0-Confirmation)
  
  전제: 상점이 0-확인(미확인 TX)을 수락
  
  공격:
    ① 공격자 → 상점: TX_A (100 JACK)
    ② 동시에 공격자 → 네트워크: TX_B (같은 UTXO → 자기에게)
    ③ TX_B가 먼저 블록에 포함되면 TX_A 무효
  
  방어:
    - 0-확인 수락 금지
    - 최소 1 확인 대기
    - 연결된 피어에서 충돌 TX 감지


Type 2: Finney Attack
  
  전제: 공격자가 채굴자
  
  공격:
    ① 공격자가 비밀리에 블록 채굴 (TX_B 포함)
    ② 블록 발견 직후 상점에 TX_A 전송
    ③ 상점이 TX_A 수락 (0-확인)
    ④ 비밀 블록 공개 → TX_B 확정, TX_A 무효
  
  방어:
    - 0-확인 수락 금지
    - 해시파워 낮은 네트워크에서 특히 주의


Type 3: Vector76 Attack (1-Confirmation)
  
  전제: Eclipse + 채굴 능력
  
  공격:
    ① 상점 노드를 Eclipse
    ② TX_A를 상점에만 보이는 블록에 포함
    ③ 상점: "1 확인!" → 물건 배송
    ④ 실제 네트워크에는 TX_B가 포함된 더 긴 체인
    ⑤ Eclipse 해제 → 상점의 블록 무효
  
  방어:
    - Eclipse 방어
    - 다수 확인 요구 (6+)
    - 여러 노드에서 교차 검증
```

---

### 9.2 TX Malleability (트랜잭션 가변성)

```
개념:
  TX의 내용은 같지만 TX ID가 바뀔 수 있는 문제
  
  원인:
    script_sig는 서명 후에도 약간 변경 가능
    (DER 인코딩 형식의 유연성)
    → TX 내용 동일, TX ID 다름
  
  공격:
    ① Alice → Bob: TX_A (ID: abc123)
    ② 공격자가 TX_A를 변조 → TX_A' (ID: def456)
    ③ TX_A'이 먼저 블록에 포함
    ④ Alice: "abc123이 확인 안 되네? 다시 보내야겠다"
    ⑤ Alice가 다시 전송 → 이중 지불!

  방어:
    Bitcoin: SegWit (서명을 TX ID 계산에서 분리)
    JackpotChain: TX ID = 서명 제외 해시 or SegWit 방식 채택
```

## 12. 핵심 요약

### 공격 분류
```
네트워크 레이어:
  Eclipse: 피해자 포위 → 정보 조작
  Sybil: 가짜 노드 대량 생성 → Eclipse 보조
  DDoS: 과부하 → 서비스 마비

합의 레이어:
  51%: 해시파워 과반 → 이중 지불, 검열
  Selfish Mining: 블록 숨기기 → 부당 이득 (33%부터)
  Block Withholding: 풀 내 배신

TX 레이어:
  Race Attack: 0-확인 이중 지불
  Finney Attack: 채굴자의 0-확인 공격
  Vector76: Eclipse + 1-확인 공격
  Malleability: TX ID 변조
```

### 핵심 방어 원칙
```
1. "노드 수"가 아닌 "해시파워"로 합의
   → Sybil의 합의 영향 차단

2. 충분한 확인 수 대기
   → Double Spending 비용 증가

3. 피어 연결 다양성
   → Eclipse 방지

4. Rate Limiting + 수수료
   → DDoS/스팸 비용 부과

5. 검증, 검증, 또 검증
   → 모든 데이터를 스스로 확인
```

### JackpotChain MVP
```
환경: 폐쇄 네트워크, 팀 내부
위험: 낮음 (신뢰 기반)
전략: 기본 검증 + 로깅 + 추후 강화
```
